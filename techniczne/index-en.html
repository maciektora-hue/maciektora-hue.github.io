What we actually keep in SQL

This is not just a song database. One database holds the structured information needed for music analysis and for mapping the content of the Russia and AuDHD projects.

01
Songs
Basic information about tracks: titles, artists, albums, playlist order, Spotify identifiers and our own internal identifiers. We also keep track of whether a song was successfully linked to its lyrics and audio recording.
02
Song lyrics
Full lyrics linked to specific songs. These are the source for later analysis of meanings, themes and changes over time.
03
Meanings and tags
A dictionary of themes and states that appear in lyrics, such as loneliness, masking, relief, anger or sensory overload. We keep their definitions, families and semantic axes, plus information about valence and directional meaning.
04
Tags assigned to lyrics
For individual lyrics we store which tags were assigned and when that tagging was created. This makes it possible to look for patterns across the whole library rather than in a single song.
05
Audio
Information about audio files and how they are linked to songs, together with detailed measurements of sound: loudness, stereo, frequency content, timbre, rhythm, tempo, key and many other features used to compare recordings.
06
Russia and AuDHD
A content map of both sections: which documents exist, how they are split into sections, their order and hierarchy, where anchors point and what descriptions are attached to individual fragments.
07
Section keywords
A shared dictionary of concepts and the assignments of those concepts to text sections, including AuDHD. This makes it possible to connect different passages by meaning even when they use different wording.
In plain English:
HTML shows the content to a person. SQL remembers what each thing is, what it belongs to, what it connects to, and what can later be counted or compared.

How the pieces are connected

01
GitHub
The main project repository: HTML, Python, configuration, supporting data and version history.
02
GitHub Pages
Publishes the static public website directly from the repository, including project landing pages and this technical section.
03
GitHub Actions
Automation stored in .github/workflows, including audits, anchor-related operations and other repeatable work on files and data.
04
Render
Hosts the public piosenki-api backend. It pulls code from this repository and runs the server-side Python application.
05
Flask + Gunicorn
Flask defines the API and server-generated pages; Gunicorn runs the Flask application as the web service on Render.
06
Turso / libSQL
The external SQLite-compatible database. The backend connects to it through libsql. The access token stays in Render environment variables rather than public HTML.
07
Flask-CORS
The bridge between the static GitHub Pages site and the Render API. It allows pages from the GitHub Pages origin to read /api/* endpoints.
Shortest version of the data path:
GitHub Pages → Render / Flask → Turso / libSQL. GitHub Actions runs alongside it as the repository automation layer.
